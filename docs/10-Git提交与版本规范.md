# VaultSync Git 提交与版本规范

> 文档编号：10 ｜ 版本：V0.1 ｜ 定位：协作规范（对全部代码与文档提交生效）

---

## 一、分支模型

| 分支 | 用途 | 规则 |
| --- | --- | --- |
| `main` | 稳定线，始终可构建 | 只接受 PR / 合并，受保护 |
| `develop` | 集成线（可选，多人时启用） | 功能分支的汇合点 |
| `feat/<阶段>-<主题>` | 功能开发 | 如 `feat/p1-kek-derivation` |
| `fix/<主题>` | 缺陷修复 | 如 `fix/p2-index-lock` |
| `docs/<主题>` | 文档修订 | 如 `docs/07-key-rotation` |
| `hotfix/<主题>` | 紧急修复 | 从 `main` 拉出，修完双线合并 |

- 安全敏感提交（`vault-crypto` / 密钥逻辑）必须单人开发、另一人（或独立会话）复核后合并；无法复核时在 `LOG.md` 记录自检清单。
- 提交前不得包含明文测试数据、密钥材料、真实用户文件。

## 二、提交信息（Conventional Commits）

格式：`<type>(<scope>): <subject>`， subject 用中文或英文均可，祈使句、不加句号、≤ 50 字。

| type | 含义 |
| --- | --- |
| `feat` | 新功能 |
| `fix` | 缺陷修复 |
| `docs` | 仅文档 |
| `refactor` | 重构（不改行为） |
| `test` | 测试补充/修改 |
| `chore` | 构建、CI、依赖、杂项 |
| `security` | 安全修复（须在正文说明影响面与缓解） |

- scope 取 crate / 模块名：`crypto`、`vault`、`p2p`、`stego`、`audit`、`core`、`app`、`ffi`、`prototype`、`docs`。
- 正文（可选）说明**为什么**；涉及安全设计时引用文档编号（如"遵循 docs/07 §3"）。
- 破坏性变更：subject 末尾加 `!`，正文以 `BREAKING CHANGE:` 开头说明迁移方式。

示例：

```
feat(crypto): 实现 Argon2id 派生 KEK 与 wrapped MK 存储

按 docs/05-01 §4 实现；降级路径（无 TEE）走主密码。
```

## 三、版本号（语义化版本 SemVer）

格式：`vMAJOR.MINOR.PATCH`，前置标签打在 `main` 上。

- **MAJOR**：密文格式 / 密钥体系不兼容变更（如 Vault 容器格式升级且旧版无法读取）。
- **MINOR**：向后兼容的功能交付（新增模块、新平台支持）。
- **PATCH**：缺陷修复、安全补丁，无接口变更。
- 0.x 阶段（当前）：`v0.x.y`，API 与格式均可能调整，MINOR 即可含破坏性变更，但须在正文与 `LOG.md` 声明。
- 每次发版：更新版本号 → 在 `LOG.md` 追加发版条目 → 打 annotated tag（`git tag -a v0.1.0 -m "..."`）→ tag 与安装包一一对应。
- 密文格式另有独立版本字段（`docs/07` 的 format version），与软件版本号无关，不得混用。
