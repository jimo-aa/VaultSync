# VaultSync 密钥轮换与格式迁移

> 文档编号：07 ｜ 版本：V0.2 ｜ 定位：**横切专项文档（不含源码）**

---

## 一、目的

定义三类演进的规范流程：密钥泄露后的轮换、密文容器格式的版本化、旧格式到新格式的迁移。V0.2 的 key-wrapping 体系（`05-01`）使多数轮换无需重加密数据。

---

## 二、密钥轮换矩阵

| 密钥 | 泄露影响域 | 轮换方式 | 是否需重加密 |
| --- | --- | --- | --- |
| 主密码 | KEK_pwd 可被离线爆破 | 修改主密码（重新 wrap MK，换 salt） | 否 |
| KEK_bio / 平台安全区 | 生物路径解封能力 | 解绑后重新绑定（重新生成 KEK_bio 与 wrap 副本） | 否 |
| FSKey（单文件） | 单个文件 | 以新 FSKey 重加密该文件（逐块流式） | 仅该文件 |
| FSK（文件夹） | 该文件夹全部文件 | 文件夹内逐文件重加密（后台低优先级任务，期间旧密文仍可读） | 仅该文件夹 |
| MK | **全库** | 见 §三 全库轮换 | 全部（分阶段） |

要点：

- **改密码 / 换生物识别永不重加密数据**——这是 V0.2 key-wrapping 体系的核心收益，作为回归测试断言。
- 文件夹/文件级轮换在引擎内以流式任务执行，进度经事件流上报，可取消、可断点续传。

---

## 三、MK 全库轮换流程（MK 泄露，如解锁态设备被完整接管）

1. 用户在其他可信设备发起"主密钥轮换"（强确认：确认短语 + 全设备告警）；
2. 各设备冻结同步写入，进入轮换会话；
3. 按文件夹逐个执行：新 MK' 派生新 FSK' → 逐文件流式重加密（新 FSKey、新 nonce 前缀）；
4. 完成后重新生成全部 wrapped 副本（KEK_pwd / KEK_bio 包装 MK'）；
5. 轮换完成事件经同步信令传播，向量时钟推进，全程写审计；
6. 旧 MK 立即 Zeroize；旧密文块按加密擦除流程清理。

**限制**：轮换期间设备离线则该设备保留旧密文副本，上线后按"追赶轮换"流程补做；轮换进度与新 MK' 的传递依赖已配对设备信任（与配对同级），文档如实标注此信任假设（见 `06` §四）。

## 四、密文格式版本化

### 4.1 Header 版本字段

```
Header 明文区:
  magic:        "VSVB"（VaultSync Vault Binary）
  format_ver:   u16（当前 = 2）
  kdf_ver:      u16（KDF 参数组编号）
  cipher_suite: u16（算法套件编号）
  chunk_cfg:    u16（CDC 参数组编号）
```

- `format_ver` 语义化递增：只增字段 = 次版本（旧引擎可读）；改语义/删除字段 = 主版本（要求双端升级，参考 `02` §5.3 ABI 握手）。
- 算法套件编号预留后量子占位（如 ML-KEM 组合模式），当前不实现。

### 4.2 兼容规则

- 引擎读取 `format_ver` 高于自身支持 → 拒绝打开并提示升级，绝不"尽力解析"；
- 写入永远使用引擎支持的最高格式版本；
- 同步两端格式版本不一致时，以低版本为准传输（降级写路径必须经审计）。

---

## 五、格式迁移流程

1. 迁移 = "读旧格式 → 写新格式"的流式复制，逐文件原子替换（临时文件 + rename）；
2. 迁移前后整文件 SHA-256 必须一致（迁移不改内容，只改容器）；
3. 中断可续传：以文件为迁移原子单元，进度记录于迁移日志；
4. 迁移由用户显式触发（设置页）或引擎在打开旧格式时建议；不自动迁移，避免用户在旧设备上意外生成不可读的新格式；
5. 全程写审计；迁移完成后旧文件按加密擦除清理。

---

## 六、测试

- 改密码后旧密文直读（零重加密断言）；
- FSKey/FSK 轮换后其他文件不受影响；
- MK 全库轮换中断恢复（离线设备追赶）；
- 格式版本向前拒绝、向后兼容矩阵；
- 迁移中断后文件不损坏（rename 原子性 + 哈希终验）。
